# Reglas de Base Designer

Este índice reúne el contrato vigente del editor y la evidencia de su implementación. Sirve para localizar reglas antes de modificar código, tanto a desarrolladores como a agentes de IA. No es una especificación del juego ni una autorización para implementar funciones pendientes.

## Clasificación de los elementos

La escena persistida tiene cinco colecciones: stations, buildings, belts, splitters y tunnels. Selection usa esos cinco tipos de objetivo. Las categorías del catálogo Stations, Buildings, Logistics, Storage y Power son agrupaciones de interfaz; no son cinco motores de comportamiento ni justifican una feature por elemento.

## Estructuras auxiliares y representación

| Estructura                                                    | Responsabilidad y límites                                                                                                                                         |
| ------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Corredores / puertas                                          | Suelo y enlaces derivados de estaciones. No tienen ID persistido, selección ni propiedad independiente; afectan apoyo y conectividad de suelo.                    |
| BuildingPort / LogisticsPort / dronePorts                     | Describen célula exterior, normal, frontera física y permisos locales. Son contratos derivados de dominio, no piezas construibles ni conexiones guardadas.        |
| BeltNetwork y puentes                                         | Grafo dirigido, productos conocidos/desconocidos, capacidades y geometría compacta. Se reconstruye desde la escena; no es simulación ni segunda fuente de verdad. |
| MachineAnalysis / ProductionAnalysis                          | Resultados derivados nominales. No se persisten, no son máquinas adicionales y no certifican producción real.                                                     |
| LED, iconos, carcasas, sockets, curvas y travesaños           | Representación. Las dimensiones decorativas y el hit target no alteran la huella, el sentido ni las capacidades del dominio.                                      |
| Clipboard, portador de arrastre, selección, cámara y previews | Estado o geometría de sesión con un dueño de UI explícito. No forman parte de la escena confirmada.                                                               |
| Notas del editor anterior                                     | No existe colección de notas en Scene. La clave antigua se preserva; eso no implica lectura o recuperación de sus funciones en el editor actual.                  |

## Estado de las reglas y de las decisiones

Cada fila distingue su estado, su distribución y el tratamiento actual. Confirmada significa que el código enlazado demuestra la regla. Aprobada pendiente significa intención acordada todavía no implementada: no describirla como comportamiento disponible. Inferida se reserva para una intención deducida sin contrato suficiente. Contradictoria se utiliza sólo cuando hay criterios incompatibles demostrables; investigar antes de decidir cuál reemplazar. Una limitación deliberada no es un bug por sí misma.

Centralizada significa que una definición o predicado gobierna sus consumidores. Distribuida con dueño significa que modelo, dominio, transacción e interfaz tienen partes diferentes de una misma regla. No toda distribución es duplicación. Duplicada sólo corresponde a la misma decisión independiente en varios lugares. Las agrupaciones de UI o diferencias de dibujo no prueban duplicación de dominio.

| Decisión                             | Contrato vigente                                                                                                                                                                                                                                                                                                                                                                                                   |
| ------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Q1 · Semántica especial de edificios | Container identifica tipos únicos y tasas nominales recibidas, sin inventario ni límite de almacenamiento. Reactor consumirá T_HydrogenFuel y generará MJ, con consumo y generación desconocidos; función de laboratorios reservada. Container está implementado; Reactor/labs permanecen pendientes, detallados en [Elementos](elementos.md#semántica-especial-q1).                                               |
| Q2 · Fallback sin receta             | Conservar provisionalmente las salidas desconocidas de edificios sin receta, incluido Container; su recepción tiene el tratamiento B08. Revisar el fallback al implementar transferencia u otras funciones especiales. No retirarlo durante una reorganización.                                                                                                                                                    |
| Q3 · Gesto de una célula             | Conservar la exigencia de dos propietarios distintos sólo al dibujar una cinta nueva de una célula. Una ruta dirigida copiada o transformada puede quedar desconectada: L02.                                                                                                                                                                                                                                       |
| Q4 · F durante borradores            | Conservar F contextual también mientras hay una herramienta/borrador activo; no debe cancelar la herramienta: I15.                                                                                                                                                                                                                                                                                                 |
| Q5 · Repetición de R                 | Conservar giros sucesivos al mantener R pulsada. C y F siguen ignorando repetición: I15.                                                                                                                                                                                                                                                                                                                           |
| Q6 · Acciones individuales heredadas | Fase 2 completada: retiradas rotateDroneStation, moveStation, removeStation, moveBuilding, rotateBuilding, moveSplitter, rotateSplitter y removeElement, sin consumidores productivos. Las operaciones activas usan transformElements/removeElements para uno o varios IDs. isStationEmpty se conserva para la captura individual del clipboard, con fallback de grupo. No hizo falta cambiar ni borrar guardados. |
| Q7 · Arquitectura                    | Conservar la arquitectura actual reforzada por módulos cohesivos y contratos compartidos. Extraer responsabilidades demostradas sin crear features por variante, clases o un motor genérico de reglas.                                                                                                                                                                                                             |

Las claves de permisos ya se comparten mediante DRONE_OUTPUT_KEYS, SPLITTER_OUTPUT_KEYS y TUNNEL_OUTPUT_KEYS. La alineación de splitter usa isAlignedSplitterLane y el encaje de edificio isBuildingOffFloor. No presentar estas unificaciones completadas como deuda pendiente ni cambiar el orden de sus mensajes.

## Cómo usar y mantener esta documentación

1. Leer [AGENTS.md](../../../../../AGENTS.md), el [README técnico](../../README.md) y sólo la sección de reglas afectada; consultar [ideas pendientes](../ideas-pendientes.md) para distinguir decisiones cerradas de trabajo futuro.
2. Partir del ID de regla y abrir sus archivos y símbolos actuales. Seguir dependencias hacia contratos compartidos y consecuencias, sin volver a auditar todo el editor por defecto.
3. Verificar el código actual: esta matriz conserva intención y evidencia, pero no garantiza que cada refactor futuro haya actualizado todos los enlaces. Un conflicto exige investigación; ni el comportamiento accidental ni un documento desactualizado autorizan cambiar reglas unilateralmente.
4. Antes de editar, identificar si se conserva una regla, se corrige una implementación o se propone un cambio funcional. Una fila pendiente, una hipótesis futura o una sugerencia arquitectónica no autoriza implementación.
5. Si cambia un símbolo o su dueño, actualizar su enlace y nombre en las filas afectadas. Evitar números de línea, estadísticas de ejecuciones y transcripciones del chat: caducan sin mejorar la navegación.
6. Al cambiar comportamiento, actualizar la fila, sus excepciones, dependencias y JSDoc cercano a la implementación. Mantener el ID; una regla retirada se marca como tal en vez de reutilizar su número para otra.
7. Añadir sólo documentación y verificación que correspondan al alcance autorizado. No afirmar que tipos, lint o compilación demuestran ausencia de regresiones funcionales, ni que comprobaciones puntuales constituyen cobertura mantenida.

No duplicar el catálogo para cumplir esta matriz, inferir reglas del juego de nombres o sufijos, añadir un motor de reglas genérico ni construir capacidades pendientes para que la documentación parezca completa. La extensión razonable conserva definiciones tipadas y predicados con responsabilidad concreta.
